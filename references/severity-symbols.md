# 严重度符号体系

招标文件常用一组符号标记条款的强制程度。**这些符号直接决定分值归宿与技术标生死，是本 skill 必须显式建模的对象。**

## 常见符号与语义

| 符号 | 常见含义 | 性质 | 漏读后果 |
| --- | --- | --- | --- |
| **★** | 实质性要求 / 关键条款 | 不满足即废标 | 直接出局 |
| **▲** | 重要技术指标 | 不满足按条扣分 | 丢分 |
| **█** | 核心指标（少数条，权重高） | 不满足按条重扣 | 丢大分 |
| **●** | 一般技术指标 | 不满足按条轻扣 | 丢小分 |
| （无符号） | 普通条款 | 不满足按条微小扣分 | 零头 |

**符号的语义以本项目评标办法的原文定义为准，不得套用上表想当然。** 上表只用于建立初始预期，实际值必须从"评标办法"章节的原文中读出，并记录到 `evidence_refs`。

## 四步建模

### 第一步：抽取

从**工作内容章节**（技术/服务要求）逐条抓符号。注意符号常出现在序号之前，形如：

```
▲（3）平台应支持不少于 200 人同时在线...
```

也有整段无符号但属于评分池的情况。

### 第二步：读扣分标准

从**评标办法章节**读出每个符号的扣分标准与声明条数，例如：

> 带▲内容每不满足一条扣 1.5 分（共 12 条）
> 带●内容每不满足一条扣 0.5 分（共 10 条）

### 第三步：反推闭合

```
computed_total = Σ( count × deduction_per_item )
closed = ( computed_total == declared_total )
```

**闭合等式是分值池质量的唯一自证。** 任何一步数错（符号认错、条数漏算、扣分标准读错），等式都对不上。

`closed == false` 时，不得标记 `COMPLETE`，必须回到原文找原因。

**但注意：闭合等式只管分值池（▲●█ 与无符号），管不了 ★。** ★ 不参与扣分池，所以"闭合成功"完全不代表 ★ 条款拆全了——这正是 v0.1.x 的翻车点。

### 第四步：符号逐行台账（v0.2.0 新增，R15 强制）

闭合等式只证明"分值池算术自洽"，证不了"条款拆全了"。所以还需要一道覆盖度对账。

**做法**：从 `source_fingerprint.json → files[tag=docx].symbol_lines` 读出**每一处**符号出现的行号，逐行登记处置，写进 `symbol_reconciliation.coverage_ledger.entries`：

| 处置 | 含义 | 必填 |
| --- | --- | --- |
| `COVERED` | 该处是独立可评审条款，已落位为 `requirement_id` | `requirement_id`（其 `severity_symbol` 必须与之相同） |
| `EXEMPT` | 该处是解释性文字 / 章节标题 / 评分规则对符号的引用 | `reason`（且不得带 `requirement_id`） |

**为什么不能只比总数（源里 30 个 ★ ↔ 产出 27 条 ★）？** 因为符号会被"引用"。本项目第 624 行的评分规则描述句，一行之内同时出现 ★▲●█ 四个符号：

> …标注"★"为本项目实质性参数…每有一项▲内容不满足扣1.5分（共12条），每有一项●内容不满足扣0.5分（共10条），每有一项█内容不满足扣5分（共3条）…

于是源文本统计出 ★30 / ▲13 / █4 / ●11，而实际条款是 ★27 / ▲12 / █3 / ●10——**每个符号都多 1**。总量比对会把这 4 处"引用"当成 4 条"漏拆"误报；反过来，如果漏拆数与引用数恰好抵消，总量比对又会漏报。

**所以只做逐行台账，不做计数比对。** 台账必须：
- 覆盖源文本全部符号行，无重复、无凭空多出；
- 每个符号的"已落位数"精确等于 `requirements[]` 中该符号的条数；
- 与源文件的集合完全一致（由 R15 拿指纹实际比对，不是自说自话）。

**★ 落在章节标题上的情况**（如「★九、教材出版」）：符号在标题行，实质要求在正文行。此时登记 `COVERED`，`reason` 写明"实质条款正文在第 N+1 行，由 REQ-xxx 承载"，`raw_excerpt` 保留标题原文。

## 三类必须登记的异常

### ① 符号漏标（`SYMBOL_GAP`）

**识别方法**：序号连续但带符号条数少一条。

```
（1）●……
（2）……            ← 序号在，符号没了
（3）●……
```

序号 (1)—(11) 共 11 条，带符号的却只有 10 条 —— 第 (2) 条漏标。

**处置**：不得自行补符号，也不得简单按"无符号"低分处理。登记 `issues[]`，并在 S3 建议按**最严假设**（实质性要求）准备材料，同时向代理机构书面澄清。

**交叉验证**（排除抽取误差）：docx XML 原文、PDF 对应页、以及 docx 包内是否存在 `numbering.xml`（自动编号可能吞掉符号）。三者一致才可确认为文件缺陷。

### ② 符号范围污染（`STAR_SCOPE`）

`★` 有时出现在**章节注释**或**品目注释**中（如"★注：……"），或在**评分规则句**里被引用，这类不计入可评审条款。按注释条数建检查表会白做工。

**识别方法**：看该符号所在行是否属于要求正文（有独立序号、有可验证动作），还是注释说明。

**处置**：在 `coverage_ledger` 里登记为 `EXEMPT` 并写明理由，**不要**为了凑数把它算成一条要求，**也不要**直接删掉不登记——删掉会让 R15 报"源文本符号未登记"。

注意区分两种"注释"：
- **纯说明性**（如"本章带★的要求为实质性要求"）→ `EXEMPT`，无实际约束；
- **有约束力的"★注"**（如"★注：响应产品属于强制采购节能产品的，须提供有效期内的认证证书，否则作无效响应处理"）→ 这是**实质性条款**，只是排版上没有编号，应当登记为 `COVERED` 并落位成独立要求。

### ③ 声明与实际不符（`COUNT_MISMATCH`）

评标办法声明"共 N 条"，与实际统计不符。二者都要记录，以**实际**为准建表，以**声明**为准判断代理机构意图。

## 输出要求

- 每条要求填 `severity_symbol` 与 `deduction_per_item`
- `scoring_pool` 填 `declared_total`、`computed_total`、`closed`、`formula`、`items[]`
- `symbol_reconciliation` 填 `declared`、`actual`、`full_document_scan`、`coverage_ledger`、`anomalies[]`

三处数字必须互相印证，且 `coverage_ledger` 必须与源文件指纹逐行一致。`validate.py` 的 R4、R5、R15 负责校验；locator 是否真的指得回源文本由 R16 校验。
