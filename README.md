# 科智汇川投标助手 · KZHC Bid Assistant

> 一个把「投标文件拆解」变成**可校验、可追溯、可复现**的 AI 工作流。
>
> 核心命题不是"帮你写标书"，而是——**如何证明自己没有漏拆招标文件里的任何一条要求。**

---

## 一、这个项目要解决什么问题

用大模型读招标文件，最大的风险不是"读不懂"，而是**读漏了却看不出来**。

招标文件是典型的"高杀伤力长文档"：

- 实质性要求（★）漏一条 → **直接废标**，而且是在开标现场才知道；
- 要求散落在不同章节（工作内容在第三章、评分办法在第五章、资格条件在第二章）；
- 规定"docx 与 pdf 不一致时以 pdf 为准"，但没人核对过两个版本；
- 评分符号（★▲█●）承载分值，漏标一处就丢一批分；
- 文件本身可能有缺陷（序号漏标符号、声明条数与实际不符）。

而市面上常见的 AI 处理方式是：**让它读完，然后输出一份"看起来专业"的摘要**。问题是——这份摘要依然自洽、依然读得通，你**无法判断它漏了多少**。

本项目的做法完全不同：**每一条结论都必须能回指到原文的行号，每一个符号都必须有去向登记，校验器不通过就不许交付。**

---

## 二、核心设计：三段流水线

固定投标主体为「四川省科智汇川人工智能科技有限责任公司」，流程可单段执行，也可端到端。

| 段 | 做什么 | 主要产物 |
| --- | --- | --- |
| **S1 分析招标文件** | 把招标原文拆成带来源、带严重度、带分值池的可追溯要求清单 | `tender_brief.json`、`招标要求摘要.md` |
| **S2 整理投标资料** | 每条要求与公司资料库逐条比对，输出"有什么、缺什么、谁去补" | `material_checklist.json`、`资料缺口与补齐清单.md` |
| **S3 辅助生成投标方案** | 得分规划、风险与澄清清单、响应章节规划、时间排期 | `bid_plan.json`、`投标方案建议书.md` |

**本 skill 不判断是否投标、不编写整本标书、不代签章、不代为提交。** 它只做"给人决策用的事实底座"。

## 三、四条铁律（违反即停止）

这四条是整个项目的灵魂，也是"AI 不许自由发挥"的边界。

| # | 铁律 | 具体约束 |
| --- | --- | --- |
| 1 | **零资料幻觉** | 公司资质、业绩、人员、财务数据只能来自 `company_profile.yaml` 或用户指定目录。缺失一律记 `MISSING`，**禁止推断、补全、类比、举例填充**。资料库为空时，S2 输出必须 **100% 为缺口**。 |
| 2 | **不猜分值** | 原文没写分值就写 `null`。所有分值必须能回指到评标办法原文的 `evidence_refs`。 |
| 3 | **不裁定冲突** | 声明条数与实际不符、格式版本冲突、符号漏标等，一律登记 `issues[]` 交人工，**不自行取舍**。 |
| 4 | **不做计数对账，只做逐行台账** | 判断"源文本要求是否都拆到了"，**禁止**用"源符号个数 == 产出条数"这种总量比对——评分规则描述句会在一行内引用多个符号。必须对源文本**每一处**符号位置逐行登记处置。 |

## 四、精华中的精华：校验体系（R1–R16）

项目内置 17 条业务校验规则（`scripts/validate.py`）与 2 份 JSON Schema，**"不通过不交付"是硬门槛**。

| 段 | 规则 | 管什么 |
| --- | --- | --- |
| S1 | R1–R3 | 需求 ID 格式与唯一、证据引句非空、非评分类不得带分值 |
| S1 | R4 | **分值池闭合**：`Σ(条数 × 单条扣分) == 声明总分` |
| S1 | R5 | 符号对账（**产出内部**三方一致） |
| S1 | R6–R8 | 未读范围已声明、主体与项目 ID 一致、有 issue 不得标 COMPLETE |
| S1 | **R15** | **符号覆盖台账完整（源文本 ↔ 产出 逐行对账）** — 见下 |
| S1 | **R16** | **locator 可回指源文本** — 见下 |
| S2 | R9–R11 | 空资料库不得出现已覆盖、确认人不得由模型填写、汇总与明细一致 |
| S3 | R12–R14 | 澄清初始为 `DRAFTED`、风险等级取值合法、章节计划须绑定需求 ID |

### R15 / R16 为什么是分水岭

这两条规则是 v0.2.0 补上的，它们把校验从"产出内部自洽"提升到"**必须与外部源文件对账**"：

- **R15 符号覆盖台账**：对源文本中每一处 ★▲█● 逐行登记 `COVERED` 或 `EXEMPT`（必须给理由）。校验器核对源符号集合与台账集合完全一致、无重复、无漏登、无凭空多出，且每个符号的"已落位条数"等于需求中该符号的条数。
- **R16 locator 可回指**：每条证据的行号必须在包内 raw 文件行数范围内，且其 `quote` 前 40 字确实出现在该行附近。**溯源链断裂会被直接拦下。**

## 五、最有说服力的一个案例：8 项规则全绿，却漏拆 26 条

这是本项目的"耻辱柱"，也是最有价值的部分——它被完整保留在 `examples/_regression_v0.1.0_should_fail/`。

v0.1.x 时期的 S1 产出，在当时的校验器下：

```
✓ R1 需求ID格式与唯一性: 共103条
✓ R2 证据引用完整性: 103条均有引句
✓ R3 非评分类不得带分值: 无
✓ R4 分值池闭合: 12×1.5 + 10×0.5 + 3×5.0 + 25×0.4 = 48.0 / 声明 48.0
✓ R5 符号条款对账: 实测 {'★': 1, '▲': 12, '█': 3, '●': 10}
✓ R6 未读范围已声明: 2 项
✓ R7 主体与项目ID一致
✓ R8 状态与issue一致性: status=REVIEW，issues=8
✗ R15 符号覆盖台账完整: entries 缺失
✗ R16 locator 可回指源文本: 103 条失准
结果: 不通过（契约 0 项 / 业务 2 项）   退出码 1
```

注意 R5 那一行——它写着"实测 `★: 1`"，**判定为通过**。因为旧规则比的是产出自己内部的三个字段，产出整体缩水时三者同步缩水，依然"自洽"。

**真相是：源文本 ★ 共 30 处，其中 27 条构成实质性条款，当时只落位了 1 条 —— 漏拆 26 条，却八项规则全绿。**

结论一句话：**只做"产出内部自洽"的校验，对覆盖度没有任何证据。校验器必须至少有一处与外部源对账。**

## 六、还自我验证：校验器自己的元测试

改过校验器的人都知道，最危险的不是"误杀"，而是**校验器悄悄退化成永远返回通过**。

所以项目里有一个 `scripts/self_test.py`：它做两件事——

1. **3 条正常路径必须放行**（防误杀）；
2. **17 类已知错误注入必须逐条被拒**（防退化）。

**基线结果 20/20。** 且规定：任何阶段改动 schema、校验规则或脚本后，必须复跑；它不通过时，**前面所有"校验通过"的结论一并作废**。

## 八、金样例：一份真实的政府采购磋商文件

`examples/四川铁道职院AI课程建设_20261010/` 是回归基线。输入是一份 **46 页、7 章**的真实政府采购磋商文件（项目编号 `N5100012026002044`，采购包预算 650,000.00 元，来源为公开政府采购公告）。

**样例中不含客户原件**（招标 docx/pdf 未随包分发），只保留抽取指纹、带行号正文与全部产出，以避免把客户资料固化进 skill。

它之所以值得当基线，是因为同时踩中了每一类真实问题：

| 现象 | 体现 |
| --- | --- |
| 要求跨章分布 | 工作内容在第三章，分值在第五章，约束在第二/四/七章 |
| 分值以池存在 | 50 条符号条款共同构成 1 个 48 分池，而非逐条分值 |
| 符号承载分值 | ▲12 / ●10 / █3 / 无符号 25；另有 ★ 实质性条款 27 条 |
| 文件自身有缺陷 | 第三章"八、虚拟仿真资源运行要求"序号 (2) **漏标 ● 符号** |
| 符号范围污染 | 第 624 行评分规则描述句一行内引用 ★▲●█，导致源文本符号计数各多 1 |
| 多格式冲突 | 文件明确规定"以 pdf 为准" |
| 资料为零 | 阴性对照：`covered=0 / partial=0`，不得出现任何已覆盖 |

### 基线结果

| 阶段 | 结果 |
| --- | --- |
| S1 | 契约 ✓ ｜ R1–R8 + R15 + R16 全通过 ｜ **120 条需求** ｜ 分值池 `12×1.5 + 10×0.5 + 3×5.0 + 25×0.4 = 48.0` 闭合 |
| S1 | 符号台账：源文本 58 处符号（★30 / ▲13 / █4 / ●11）全部登记；★ 维度 `COVERED 27 / EXEMPT 3` |
| S2 | 契约 ✓ ｜ `covered=0 / partial=0 / missing=96 / expired=0 / review=24` ｜ `gate_missing=48` |
| S3 | 契约 ✓ ｜ R12–R14 全通过 ｜ `plan_status=BLOCKED` |
| self_test | **20/20**（3 条正常路径 + 17 类错误注入逐条被拒） |

## 九、快速开始

### 1. 环境准备

脚本依赖 `pypdf`（抽 pdf）、`python-docx`（抽 docx）、`jsonschema`：

```bash
python -m pip install pypdf python-docx jsonschema
python -c "import pypdf, docx, jsonschema; print('deps OK')"
```

> ⚠️ 用无依赖的 python 直接跑时，docx 往往**仍能抽出**，只有 pdf 会抛 `ModuleNotFoundError` —— 于是产物里静默少一份 pdf 指纹，`format_diff` 那句"docx 与 pdf 均已抽取"就成了空话。**先自检再动手。**

### 2. 复跑金样例的回归验证

```bash
# 校验三份产出（源文件须与产出同目录，R15/R16 才会真正执行）
python scripts/validate.py --stage S1 --input examples/四川铁道职院AI课程建设_20261010
python scripts/validate.py --stage S2 --input examples/四川铁道职院AI课程建设_20261010
python scripts/validate.py --stage S3 --input examples/四川铁道职院AI课程建设_20261010

# 校验器自身元验证，必须是 20/20
python scripts/self_test.py
```

### 3. 看那份"必须失败"的对照样本

```bash
python scripts/validate.py --stage S1 --input examples/_regression_v0.1.0_should_fail
# → R1—R8 全绿（旧规则看不出问题），R15、R16 双红，退出码 1
```

### 4. 跑自己的招标文件

```bash
python scripts/extract_tender.py --input <招标文件.docx> --input <招标文件.pdf> --output-dir <工作目录>
# 然后按 references/runbook.md 走 S1 七步
```

## 十、一个反直觉的设计原则

项目里有一节叫「对外文档引用的数字」，规定：**任何引用本 skill 数字的对外材料（答辩手册、汇报、验收单、说明书）必须标注数据采集时间与当时的 skill 版本，并给出核对命令；在 skill 发生任何改动后一律视为过期。**

原因很实在：这类文档的失效方式是"**依然读得通、依然自洽**"，它不会报错。

本 skill 的答辩手册初稿即因此失效——写于 v0.1.1，数小时后技能升到 v0.2.0，其中 **8 处数字（文件数、规则数、需求条数、自测基线、S2 各状态计数）全部过期而无人察觉**。

> **数字是对账出来的，不是写出来的。**

## 十二、边界与声明

- **不代替人的判断**：所有 `issues[]`、确认人字段、投标决策一律交人工。
- **不伪造**：出现伪造或涂改痕迹、要求伪造资质、要求代替签章提交时，**停止并列出所缺输入或授权**。
- **`processing_status`** 仅 `COMPLETE / REVIEW / BLOCKED` 三值，**只代表本段处理状态，不代表投标结论**。
- 样例中的招标文件内容来源于公开政府采购公告，仅用于回归验证；客户原件未随包分发。

## 十三、已知未完成项

1. **S2 未接真实资料**：需填 `company_profile.yaml` 并放入真实材料后重跑，才能得到真实缺口清单而非阴性对照。匹配逻辑本身已用虚构数据做过敏感性验证（三组单变量对照，五类状态全部可达）。
2. **★ 台账建议人工抽查 ≥30%**：台账由模型登记，规则只能保证"登记完整、符号自洽"，不能保证"业务判断正确"。每条都留了 `reason` 与 `raw_excerpt`，抽查成本很低。
3. **`deadline` 为 null**：金样例文件正文注明"提交截止时间详见采购公告"，不在文件内，已登记 `DEADLINE_NOT_IN_DOCUMENT`。
